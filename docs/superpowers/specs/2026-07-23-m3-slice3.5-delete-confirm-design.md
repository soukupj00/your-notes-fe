# M3 Slice 3.5 - Confirm-before-delete retrofit

## Context

M3 adds attachments and rich media.
Slice 1 shipped inline images, Slice 2 inline audio (and the media-agnostic core under `src/components/editor/extensions/attachments/`), and Slice 3 inline video.

Along the way each in-editor media NodeView grew a delete affordance, but inconsistently:

- `AudioNodeView.tsx` and `VideoNodeView.tsx` each render a `Trash2` icon-button that calls `props.deleteNode()` **directly on click** - one misclick silently removes the attachment node from the document with no confirmation.
- `ImageNodeView.tsx` has **no delete button at all** - an inserted image can only be removed via editor selection + Backspace.

This slice is a small retrofit that makes node deletion consistent and safe: one shared, media-agnostic confirm-before-delete control, wired into audio and video (replacing their bare click handlers) and added to image (new button, same behavior).

**Deletion timing is unchanged.**
Removing a node only edits the TipTap document (`props.deleteNode()` drops the node from the doc).
It does **not** touch Dexie.
The attachment's bytes are reclaimed later by `collectOrphans` when the editor dialog closes (`NoteEditorDialog.tsx:163`, `useAttachmentActions.collectOrphans`), which deletes any `attachments` row for the note that the saved Body no longer references.
That GC path, and its timing, are out of scope here.
This slice inserts a confirmation step in front of the existing `deleteNode()` call and nothing more - a future reader should not read new deletion-timing or blob-lifecycle logic into it.

The control is designed to be reused by Slice 4 (generic file attachments) and Slice 5 (Excalidraw), so it is generic - not audio/video-specific.

## Scope

**In scope**

- One shared `ConfirmDeleteButton` component under `src/components/editor/extensions/attachments/`: a `Trash2` icon-button trigger that opens an "Are you sure?" dialog and calls a supplied `onConfirm` callback only when the user confirms.
- Built on the existing Radix `Dialog` primitive (`src/components/ui/dialog.tsx`) - no new dependency, no new UI primitive.
- Retrofit `AudioNodeView` and `VideoNodeView` to route their existing (editable-only) delete buttons through it, replacing the bare `onClick={() => props.deleteNode()}`.
- Add a delete button to `ImageNodeView`, matching Video's visual pattern (icon-button in a flex row, shown only when `props.editor?.isEditable`, `aria-label` via i18n), also routed through the shared control.
- A shared confirm-dialog i18n string set (`attachments.confirmDelete.title/description/confirm/cancel`) in both locales, plus a new per-kind `editor.image.delete` label (audio and video already have `editor.{audio,video}.delete`).
- Tests landing in the same change (pragmatic TDD).

**Explicitly out of scope**

- Any change to blob deletion or GC timing - `collectOrphans` at dialog close is untouched (`NoteEditorDialog.tsx:163`).
- Undo/redo semantics of `deleteNode()` - the existing TipTap history behavior is unchanged (a confirmed delete remains a single undoable step).
- A generic reusable `AlertDialog` shadcn primitive - none exists in `src/components/ui/`, and adding `@radix-ui/react-alert-dialog` is unnecessary for this retrofit; the existing `Dialog` is sufficient.
- Any Dexie schema, model, or new attachment kind.
- Confirmation for non-attachment nodes (text, lists, etc.).

## Design

### 1. Shared control - `extensions/attachments/ConfirmDeleteButton.tsx` (new)

A self-contained trigger + dialog. It renders the same `Trash2` icon-button the NodeViews render today (the trash styling moves here, so it is defined once) as the dialog trigger, manages its own open/close state, and calls `onConfirm` only on confirm.

Props:

```ts
import type { TFunction } from '../button-types';

export interface ConfirmDeleteButtonProps {
  /** Invoked once, only when the user confirms. In every NodeView this is
   *  `() => props.deleteNode()` - editor-only, never touches Dexie. */
  onConfirm: () => void;
  /** Per-kind aria-label for the trigger, e.g. t('editor.video.delete'). Also
   *  the accessible name a test queries by. */
  label: string;
  /** Resolves the shared attachments.confirmDelete.* dialog strings. NodeViews
   *  pass their deps.t. */
  t: TFunction;
}
```

Behavior:

- Trigger: `<DialogTrigger asChild>` wrapping a `<button type="button" aria-label={label}>` with the trash styling previously inlined in the NodeViews (`flex size-8 shrink-0 items-center justify-center rounded-full text-muted-foreground hover:bg-destructive/10 hover:text-destructive`) and an `icons.Trash2` glyph (`size-4`).
- Dialog: `<DialogContent className="sm:max-w-sm">` with a `DialogHeader` (`DialogTitle` = `t('attachments.confirmDelete.title')`, `DialogDescription` = `t('attachments.confirmDelete.description')`) and a `DialogFooter` with two `Button`s:
  - Cancel: `variant="outline"`, `t('attachments.confirmDelete.cancel')`, closes the dialog (no callback).
  - Confirm: `variant="destructive"`, `t('attachments.confirmDelete.confirm')`, closes the dialog **then** calls `onConfirm()`.
- Open state is local `useState(false)`, driven by `Dialog`'s `open`/`onOpenChange`. Radix portals the content to `document.body`, so it escapes the editor's contentEditable/atom-node DOM cleanly (the existing `NoteEditorDialog` already relies on the same portal behavior).

Rationale for a **component** (not a `useConfirmDelete()` hook): all three consumers are identical - an icon delete button that guards `deleteNode()`. A single component that owns the trigger, the dialog, and the wiring makes each call site one line and keeps the trash styling in exactly one place. A hook would re-expose trigger/dialog assembly to every caller for no benefit here. (Slices 4/5 consume the same shape.)

### 2. `extensions/attachments/index` re-export (optional, follow existing convention)

There is no barrel in `attachments/` today (consumers import files directly, e.g. `../attachments/useAttachmentObjectUrl`). Keep that convention: NodeViews import `ConfirmDeleteButton` directly from `../attachments/ConfirmDeleteButton`. No new barrel file.

### 3. `AudioNodeView.tsx` retrofit

Replace the locally-built `deleteButton` (the bare `<button onClick={() => props.deleteNode()}>` block) with the shared control, keeping the exact `canDelete` gate:

```tsx
import { ConfirmDeleteButton } from '../attachments/ConfirmDeleteButton';

const canDelete = props.editor?.isEditable ?? false;
const deleteButton = canDelete ? (
  <ConfirmDeleteButton
    onConfirm={() => props.deleteNode()}
    label={deps.t('editor.audio.delete')}
    t={deps.t}
  />
) : null;
```

`deleteButton` is still rendered in both the `missing` branch and the ready player row exactly where it is today; `icons.Trash2` and its inline `<button>` markup are removed from this file (they now live in `ConfirmDeleteButton`).

### 4. `VideoNodeView.tsx` retrofit

Identical change with `editor.video.delete`. The `deleteButton` stays in the `missing` branch and the ready flex row (`flex items-start gap-3`) unchanged; only its construction moves to `ConfirmDeleteButton`.

### 5. `ImageNodeView.tsx` - add the delete button

`ImageNodeView` currently renders only the `<img>` / loading / missing states in a bare `NodeViewWrapper`. Add an editable-only delete button matching Video's pattern:

- Compute `const canDelete = props.editor?.isEditable ?? false;` and a `deleteButton` (same `ConfirmDeleteButton` construction, `label={deps.t('editor.image.delete')}`).
- Wrap the ready `<img>` in a `flex items-start gap-3` row with the `deleteButton` beside it (mirroring `VideoNodeView`'s ready layout), so the button sits at the image's top-right start without overlapping.
- Add `deleteButton` to the `missing` branch too, mirroring audio/video's missing layout (`flex items-center gap-3 ... border-dashed`, message in a `flex-1 text-center` span, button after).
- The `loading` skeleton is unchanged (no attachment resolved yet, nothing to delete).

## Data flow

1. User clicks the trash icon in an editable image/audio/video NodeView -> `ConfirmDeleteButton` sets its local `open` to true -> Radix `Dialog` portals the confirm content to `document.body`.
2. User clicks **Cancel** (or dismisses via overlay/Esc) -> dialog closes, `onConfirm` never fires, the node is untouched.
3. User clicks **Remove** -> dialog closes, then `onConfirm()` runs, which is `() => props.deleteNode()` -> TipTap removes the node from the document. Nothing else runs synchronously; no Dexie call.
4. Later, when the note's editor dialog closes, the existing `collectOrphans(noteId, extractAttachmentIds(body))` (`NoteEditorDialog.tsx:163`) deletes the now-unreferenced `attachments` row. This slice adds no code on that path.

## Error handling

- There are no new async operations and no new failure modes: the control only toggles local state and calls a synchronous editor command.
- If `props.editor` is undefined or the editor is read-only, `canDelete` is false and no delete button (and therefore no dialog) is rendered - the current audio/video behavior, now also applied to image.
- Radix `Dialog` provides focus trapping, Esc-to-close, and overlay-click-to-close for free; a dismissed dialog is equivalent to Cancel.

## Assumptions

- **Existing `Dialog` primitive, not a new `AlertDialog`** - keeps the retrofit dependency-free; the `Dialog` gives the same confirm affordance. If Slices 4/5 later want the stricter `alertdialog` ARIA role, promoting `ConfirmDeleteButton` to a Radix AlertDialog is a localized change behind the same props.
- **A component, not a `useConfirmDelete()` hook** - all consumers are the identical icon-button-guards-`deleteNode` shape; the component keeps call sites to one line and the trash styling in one place. The prop surface (`onConfirm`, `label`, `t`) is generic enough for file/Excalidraw nodes.
- **Copy** - "Remove this attachment?" / "It will be removed from this note. This cannot be undone once you close the note." reflects the real semantics: the node leaves the doc immediately, but the blob is only GC'd (irreversibly) at dialog close. Wording is trivially adjustable.
- **Deletion timing is unchanged** - this slice only inserts a confirmation before the pre-existing `props.deleteNode()`; `collectOrphans` at `NoteEditorDialog.tsx:163` still owns blob reclamation and its timing.
